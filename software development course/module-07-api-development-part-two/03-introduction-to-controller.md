# ০৩. Introduction to Controller - Why and How to Implement This

আগের লেসনে আমরা রুটগুলোকে আলাদা ফাইলে ভাগ করে ফেললাম, কিন্তু একটা জিনিস খেয়াল করলে দেখবে — প্রতিটা রুটের পাশে এখনো একটা করে ফাংশন লেখা আছে, যেখানে আসল কাজটা হচ্ছে। যদি এই ফাংশনগুলো ছোট হয় (এক-দুই লাইন), তাহলে সমস্যা নেই। কিন্তু বাস্তব জীবনে একটা রুট হ্যান্ডলার প্রায়ই অনেক কাজ করে — ডেটাবেজ থেকে তথ্য আনা, সেটাকে যাচাই করা, হিসাব করা, তারপর সঠিক ফরম্যাটে রেসপন্স পাঠানো। এই সবকিছু যদি `routes/userRoutes.js` ফাইলের ভেতরেই লেখা হয়, তাহলে রুট ফাইলটা আর "রুট কোথায় যাবে সেটার তালিকা" থাকে না — এটা হয়ে যায় একটা জগাখিচুড়ি, যেখানে "ঠিকানা" আর "কাজ" মিশে যায়।

এই সমস্যার সমাধান হলো **Controller**। ধারণাটা রেস্টুরেন্টের সাথে তুলনা করলে সহজে বোঝা যায় — যেটা আমরা আগেও ব্যবহার করেছি। **Router হলো রেস্টুরেন্টের ফ্রন্ট ডেস্ক বা ওয়েটার** — সে অর্ডার নেয়, বলে দেয় কোন টেবিলের জন্য কোন খাবার, কিন্তু নিজে রান্না করে না। **Controller হলো রেস্টুরেন্টের কিচেন** — এখানেই আসল কাজটা হয়, রান্নার প্রতিটা ধাপ এখানে ঘটে। ওয়েটার শুধু অর্ডারটা কিচেনে পাঠায় আর রান্না শেষ হলে খাবারটা টেবিলে নিয়ে যায়। এই বিভাজনের একটা বড় সুবিধা হলো — ওয়েটার বদলালেও কিচেনের রেসিপি বদলায় না, আর রেসিপি উন্নত করলেও ওয়েটারের কাজের ধরন বদলায় না। দুটো সম্পূর্ণ আলাদা দায়িত্ব, আলাদা জায়গায় থাকে।

সফটওয়্যারের ভাষায় এটাকে বলে **Separation of Concerns** — প্রতিটা অংশের একটাই নির্দিষ্ট দায়িত্ব থাকা উচিত। এই চিন্তাটাই বড় বড় ফ্রেমওয়ার্কে **MVC (Model-View-Controller)** নামের একটা জনপ্রিয় প্যাটার্নের ভিত্তি — যেখানে Model ডেটা সামলায়, View (আমাদের ক্ষেত্রে JSON রেসপন্স) ইউজারকে যা দেখানো হবে সেটা সামলায়, আর Controller মাঝখানে থেকে ব্যবসায়িক লজিকটা চালায়। আমরা এখনো পুরোপুরি Model নিয়ে কথা বলিনি (সেটা Module 8-এ, ডেটা মডেলিং নিয়ে বিস্তারিত আলোচনায় আসবে), কিন্তু Controller-এর ধারণাটা এখনই কাজে লাগানো যায়।

চলো বাস্তবে করে দেখাই। প্রথমে একটা `controllers/userController.js` ফাইল বানাই:

```javascript
// controllers/userController.js

const getAllUsers = (req, res) => {
  // বাস্তবে এখানে ডেটাবেজ থেকে ইউজার তালিকা আনা হতো
  const users = [
    { id: 1, name: 'রহিম' },
    { id: 2, name: 'করিম' }
  ];
  res.status(200).json({ success: true, data: users });
};

const getUserById = (req, res) => {
  const { id } = req.params;
  res.status(200).json({ success: true, data: { id, name: 'রহিম' } });
};

const createUser = (req, res) => {
  const { name, email } = req.body;
  // Module 6 লেসন ৫-এর ভ্যালিডেশন এখানেই বসবে, রুটে না
  if (!name || !email) {
    return res.status(400).json({ success: false, message: 'নাম আর ইমেইল আবশ্যক' });
  }
  const newUser = { id: Date.now(), name, email };
  res.status(201).json({ success: true, data: newUser });
};

module.exports = { getAllUsers, getUserById, createUser };
```

এবার `routes/userRoutes.js` ফাইলটা হয়ে যাবে অনেক পরিষ্কার — এটা শুধু বলে দেবে কোন পাথ, কোন মেথড, কোন controller ফাংশনে যাবে:

```javascript
// routes/userRoutes.js
const express = require('express');
const router = express.Router();
const { getAllUsers, getUserById, createUser } = require('../controllers/userController');

router.get('/', getAllUsers);
router.get('/:id', getUserById);
router.post('/', createUser);

module.exports = router;
```

এখন রুট ফাইলটা পড়লেই তুমি এক নজরে বুঝে যাবে এই রিসোর্সে কী কী এন্ডপয়েন্ট আছে, আর প্রতিটার আসল কাজ কোথায় খুঁজতে হবে সেটাও স্পষ্ট। Module 6 লেসন ৩-এ আমরা যে POST request-এর ভেতরের অ্যানাটমি (headers, body) নিয়ে কথা বলেছিলাম, সেই `req.body`-টাই এখন controller ফাংশনের ভেতরে ব্যবহৃত হচ্ছে, কিন্তু এই ডেটাটা রুট হয়ে ঠিক জায়গায় পৌঁছানো পর্যন্ত রাউটার তার কাজ করেছে মাত্র — বিশ্লেষণ, যাচাই, প্রক্রিয়াকরণ, সব হচ্ছে কন্ট্রোলারে।

```mermaid
sequenceDiagram
    participant C as Client
    participant R as Router (Front Desk)
    participant Ctrl as Controller (Kitchen)
    C->>R: POST /users {name, email}
    R->>Ctrl: createUser(req, res) কল করো
    Ctrl->>Ctrl: ডেটা যাচাই, প্রসেস
    Ctrl-->>C: 201 Created + নতুন ইউজার
```

এই বিভাজনের সবচেয়ে বড় ব্যবহারিক সুবিধা বোঝা যায় যখন প্রজেক্ট বড় হতে থাকে — নতুন একজন ডেভেলপার টিমে যোগ দিলে, তাকে পুরো কোডবেজ না বুঝেই বলা যায় "শুধু `controllers` ফোল্ডারটা দেখো, ওখানেই ব্যবসায়িক লজিক।" আর টেস্ট লেখার সময়ও এই আলাদা করে রাখা ফাংশনগুলো (`getAllUsers`, `createUser`) স্বাধীনভাবে টেস্ট করা অনেক সহজ হয়, কারণ এগুলো Express-এর রাউটিং সিস্টেমের সাথে জড়িয়ে নেই।

router আর controller মিলিয়ে এখন আমাদের কাছে একটা পরিষ্কার, স্তরভিত্তিক স্ট্রাকচার আছে। কিন্তু এখনো একটা গুরুত্বপূর্ণ প্রশ্ন বাকি — প্রতিটা request-এর জন্য এমন কিছু কাজ থাকে যা প্রায় সব রুটেই দরকার হয়, যেমন "ইউজার লগইন করা আছে কিনা যাচাই করা" বা "request-টা লগ করে রাখা"। এই একই কাজ কি প্রতিটা controller ফাংশনে বারবার লিখতে হবে? এই প্রশ্নের উত্তর নিয়েই পরের লেসনে আমরা যাচ্ছি — **Middleware**-এর জগতে।
