# ০২. Routing System in FastAPI Application

একটা শহরের কথা চিন্তা করো। শহরে হাজারটা ঠিকানা আছে — বাসাবাড়ি, দোকান, হাসপাতাল, স্কুল। যদি প্রতিটা ঠিকানার কোনো নিয়ম না থাকতো, প্রতিটা রাস্তার নাম এলোমেলো হতো, তাহলে ডাকপিওনের জন্য চিঠি পৌঁছানো অসম্ভব হয়ে যেতো। তাই শহরে একটা ঠিকানা-ব্যবস্থা থাকে — এলাকা, রাস্তা, বাড়ি নম্বর — যাতে যে কেউ ঠিকানা দেখেই বুঝতে পারে জিনিসটা ঠিক কোথায় যাবে।

একটা FastAPI অ্যাপ্লিকেশনও ঠিক এরকম একটা "শহর"। প্রতিটা URL একটা ঠিকানা, আর **routing** হলো সেই ব্যবস্থা যেটা ঠিক করে দেয় কোন ঠিকানায় রিকোয়েস্ট এলে কোন কোড চলবে। Module 4-এ আমরা ইতিমধ্যে দেখেছি কীভাবে `@app.get()` দিয়ে একটা সাধারণ রুট বানানো যায়, আর query আর path parameter দিয়ে কীভাবে ঠিকানার ভেতরে অতিরিক্ত তথ্য পাঠানো যায়। এখন আমরা পুরো routing সিস্টেমটা আরও গভীরভাবে বুঝবো — শুধু GET না, বাকি HTTP মেথডগুলো নিয়েও।

আসলে একটা ঠিকানা শুধু "কোথায় যাচ্ছো" বলে না, "কী করতে যাচ্ছো" সেটাও বলা দরকার — আর সেটাই HTTP মেথডের কাজ। ধরো তুমি একটা লাইব্রেরির ঠিকানায় গেলে। "বই দেখতে যাচ্ছি" (GET), "নতুন বই জমা দিতে যাচ্ছি" (POST), "একটা বইয়ের তথ্য বদলাতে যাচ্ছি" (PUT/PATCH), আর "একটা বই লাইব্রেরি থেকে সরিয়ে ফেলতে যাচ্ছি" (DELETE) — এই চারটা কাজ একই ঠিকানার (যেমন `/books`) সাথে সম্পর্কিত হলেও সম্পূর্ণ ভিন্ন উদ্দেশ্য বহন করে। FastAPI-এ প্রতিটা মেথডের জন্য আলাদা decorator আছে:

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/books")
def list_books():
    return {"message": "সব বইয়ের তালিকা"}


@app.post("/books", status_code=201)
def create_book():
    return {"message": "নতুন বই যোগ হলো"}


@app.put("/books/{book_id}")
def update_book(book_id: int):
    return {"message": f"বই {book_id} আপডেট হলো"}


@app.delete("/books/{book_id}")
def delete_book(book_id: int):
    return {"message": f"বই {book_id} মুছে ফেলা হলো"}
```

লক্ষ্য করো, `/books` আর `/books/{book_id}` — একই "এলাকা" নিয়ে চারটা ভিন্ন রুট তৈরি হয়েছে, প্রতিটার কাজ ভিন্ন। এই প্যাটার্নটার একটা সুন্দর নাম আছে ইন্ডাস্ট্রিতে — **RESTful routing** — যেখানে URL বলে দেয় "কোন রিসোর্স নিয়ে কাজ করছি" (যেমন `books`), আর HTTP মেথড বলে দেয় "কী কাজ করছি" (দেখা, তৈরি করা, বদলানো, মোছা)। আমরা এই প্যাটার্নটা Module 7-এ আরও গভীরে নিয়ে যাবো।

FastAPI কীভাবে ঠিক করে কোন রুট চলবে, সেটার একটা ছবি দেখা যাক:

```mermaid
flowchart TD
    Req["Client Request আসলো: POST /books"] --> Match{"FastAPI রুটগুলো একে একে চেক করে"}
    Match -->|"method='GET', path='/books' — মিলছে না"| Skip1["এড়িয়ে যাও"]
    Match -->|"method='POST', path='/books' — মিলে গেছে!"| Handler["এই রুটের path operation function চালাও"]
    Handler --> Response["Response পাঠাও"]
```

FastAPI রুটগুলো উপর থেকে নিচে ক্রমানুসারে চেক করে, প্রথম যেটার সাথে method আর path দুটোই মিলে যায়, সেটাই চালায়। এই কারণে রুট লেখার ক্রমও মাঝে মাঝে গুরুত্বপূর্ণ — যেমন `/books/{book_id}` এর আগে যদি `/books/featured` লেখা হয়, তাহলে `featured` শব্দটা ভুল করে `{book_id}` হিসেবে ধরা পড়তে পারে যদি ক্রম উল্টো হয়।

একটা বাস্তব অ্যাপ্লিকেশনে হয়তো শতশত রুট থাকবে — সব একটা মাত্র ফাইলে লিখলে সেটা অগোছালো হয়ে যাবে, ঠিক যেমন একটা শহরের সব ঠিকানা যদি একটাই কাগজে এলোমেলোভাবে লেখা থাকতো। তাই বাস্তব প্রজেক্টে ডেভেলপাররা FastAPI-এর `APIRouter` ব্যবহার করে রুটগুলোকে আলাদা ফাইলে ভাগ করে ফেলে, বিষয় অনুযায়ী — যেমন `routers/users.py`, `routers/books.py`:

```python
# routers/books.py
from fastapi import APIRouter

router = APIRouter(prefix="/books", tags=["books"])


@router.get("/")
def list_books():
    return {"message": "সব বইয়ের তালিকা"}


@router.post("/", status_code=201)
def create_book():
    return {"message": "নতুন বই যোগ হলো"}
```

```python
# main.py
from fastapi import FastAPI
from routers import books

app = FastAPI()
app.include_router(books.router)
```

এখানে `app.include_router(books.router)` লাইনটা বলে দিচ্ছে — "`books` router-এ যত রুট আছে, সব মূল অ্যাপ্লিকেশনে যুক্ত করে দাও।" আর `APIRouter(prefix="/books", ...)`-এ `prefix` লেখার মানে হলো, রাউটারের ভেতরে `/` লিখলেই সেটা আসলে `/books` বোঝাবে — ঠিক যেমন Express-এ `app.use('/books', bookRoutes)` লিখে path prefix বসানো হতো, এখানে সেই কাজটা `prefix` প্যারামিটার দিয়ে হয়, আলাদা করে `app.include_router()`-এ path লিখতে হয় না (চাইলে `include_router(books.router, prefix="/books")` লিখেও prefix দেয়া যায়, দুটো উপায়ই চলে)। এভাবে একটা বড় অ্যাপ্লিকেশনও ছোট ছোট, পরিষ্কার অংশে ভাগ হয়ে যায় — ঠিক যেমন একটা শহরকে এলাকা অনুযায়ী ভাগ করলে ম্যাপ পড়া সহজ হয়।

একটা প্রোডাকশন-লেভেল ভুল যেটা বড় অ্যাপ্লিকেশনে খুব সাধারণ — সব router-কে একটাই বিশাল ফাইলে prefix ছাড়া রেখে দেয়া, বা একই resource-এর রুট দুই জায়গায় ছড়িয়ে রাখা (যেমন `users.py`-এ কিছু user route, আবার `admin.py`-এ আরও কিছু user route)। এতে দুইটা সমস্যা হয় — প্রথমত, কোনো একটা এন্ডপয়েন্ট খুঁজে পেতে পুরো কোডবেস খুঁজতে হয়; দ্বিতীয়ত, `prefix` না দিলে প্রতিটা রুটে পুরো path (`/books/`, `/books/{id}`) হাতে লিখতে হয়, যেটা টাইপো আর অসামঞ্জস্যতার ঝুঁকি বাড়ায়। তাই বাস্তব প্রজেক্টে প্রতিটা resource-এর জন্য একটা করে router ফাইল, prefix দিয়ে সংগঠিত রাখা, আর `tags` প্যারামিটার দিয়ে দলবদ্ধ করা — এটাই ভালো অভ্যাস, বিশেষ করে `/docs` পেজে যখন এন্ডপয়েন্টগুলো গোছানোভাবে দেখানো দরকার হয়।

এখন আমাদের কাছে ঠিকানা-ব্যবস্থা তৈরি হয়ে গেছে GET, POST, PUT, DELETE-এর জন্য। কিন্তু POST রিকোয়েস্টে ক্লায়েন্ট আসলে ঠিক কী পাঠায়, আর সেটা কীভাবে ব্যাকএন্ড গ্রহণ করে — সেই পুরো গল্পটা এখনো বাকি। পরের লেসনে আমরা একটা POST endpoint-এর ভেতরের অ্যানাটমি খুঁটিয়ে দেখবো।
