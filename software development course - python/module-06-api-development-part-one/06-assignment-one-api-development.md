# ০৬. Assignment: One API Development

এতক্ষণ আমরা যা শিখেছি, সেগুলো ছোট ছোট টুকরো টুকরো উদাহরণে দেখেছি — কখনো একটা `/tasks` রুট, কখনো একটা `@field_validator` দিয়ে ভ্যালিডেশন। কিন্তু বাস্তব দক্ষতা তৈরি হয় তখনই, যখন এই সব টুকরো একসাথে বসিয়ে নিজের হাতে একটা সম্পূর্ণ, কার্যকর জিনিস বানানো যায় — ঠিক যেমন একজন ছুতোর মিস্ত্রি আলাদা আলাদা কৌশল শেখার পর, একদিন সত্যিকারের একটা আলমারি বানিয়ে ফেলে, প্রথম থেকে শেষ পর্যন্ত নিজের হাতে। এই লেসনটা সেই দিন — এখন তোমার পালা।

**তোমার কাজ:** একটা "Notes API" বানাও — এমন একটা ব্যাকএন্ড সিস্টেম, যেখানে ব্যবহারকারী ছোট ছোট নোট তৈরি করতে পারবে, সব নোট দেখতে পারবে, আর নির্দিষ্ট একটা নোট মুছে ফেলতে পারবে। এটা শুনতে সাধারণ মনে হলেও, এর ভেতরে এই পুরো মডিউলে শেখা প্রতিটা ধারণা লুকিয়ে আছে।

প্রথমেই বসে চিন্তা করো একটা "Note"-এর মডেল কেমন হওয়া উচিত — ঠিক যেমন আমরা আগের লেসনে Task মডেল নিয়ে ভেবেছিলাম। একটা নোটের কী কী বৈশিষ্ট্য থাকা দরকার? নিশ্চয়ই একটা লেখা বা বিষয়বস্তু (`content`) থাকবে, যেটা ছাড়া একটা নোট অর্থহীন। হয়তো একটা `id` থাকবে, যেটা সার্ভার নিজে থেকেই বসাবে। আর হয়তো একটা `created_at` থাকবে, যাতে বোঝা যায় নোটটা কখন তৈরি হলো। মডেলটা কাগজে বা মাথায় স্পষ্ট করে নেয়ার পরই কোডে হাত দাও — একটা `NoteCreate` Pydantic মডেল (ক্লায়েন্ট থেকে যা আসবে) আর দরকার হলে একটা আলাদা `Note` মডেল (ক্লায়েন্টকে যা ফেরত পাঠাবে) — এটাই এই মডিউলের সবচেয়ে গুরুত্বপূর্ণ শিক্ষা।

তারপর routing সাজাও, FastAPI-এর `APIRouter` বা সরাসরি `app` দিয়ে। তোমার অন্তত এই তিনটা endpoint থাকা দরকার:

- `GET /notes` — সব নোটের তালিকা ফেরত দেবে
- `POST /notes` — নতুন একটা নোট তৈরি করবে, request body থেকে `content` নিয়ে
- `DELETE /notes/{note_id}` — নির্দিষ্ট `note_id`-এর নোটটা মুছে ফেলবে

চাইলে আরেকটা বাড়তি endpoint যোগ করে চ্যালেঞ্জ বাড়াতে পারো — `GET /notes/{note_id}`, যেটা একটা নির্দিষ্ট নোট খুঁজে বের করে দেখাবে। এভাবেই একটা ছোট, বাস্তব RESTful API-এর গঠন তৈরি হয়ে যাবে, ঠিক যেমনটা আমরা Routing লেসনে দেখেছিলাম।

`POST /notes` endpoint বানানোর সময় মনে রাখতে হবে দুটো জিনিস — প্রথমত, request body-টা একটা Pydantic মডেল (`NoteCreate`) দিয়ে টাইপ হিন্ট করা আছে কিনা, নইলে FastAPI বুঝবেই না body থেকে ডেটা নিতে হবে। দ্বিতীয়ত, ভ্যালিডেশন। কোনো অবস্থাতেই ধরে নিও না যে ক্লায়েন্ট সবসময় সঠিক ডেটা পাঠাবে। Pydantic-এর টাইপ চেকিং (`content: str`) অনেকখানি কাজ নিজে থেকেই করে দেবে — `content` না থাকলে বা string না হলে FastAPI স্বয়ংক্রিয়ভাবে `422` পাঠাবে। কিন্তু খালি স্ট্রিং (`""`) পাঠানোটা টাইপ চেকিং পাস করে যাবে, তাই সেটা ঠেকানোর জন্য তোমাকে নিজে একটা `@field_validator` লিখতে হবে, যাতে trimmed করার পর কিছু না থাকলে একটা স্পষ্ট error ওঠে।

`DELETE /notes/{note_id}` endpoint-এ একটা গুরুত্বপূর্ণ প্রশ্নের মুখোমুখি হবে — যদি ক্লায়েন্ট এমন একটা `note_id` পাঠায় যেটা আসলে অস্তিত্বই নেই, তখন কী করবে? এখানেই status code-এর জ্ঞান কাজে লাগবে — এটা কোনো সার্ভার-সমস্যা না (তাই `500` না), এটা এমন একটা অনুরোধ যেটা মেলে না কোনো বাস্তব রিসোর্সের সাথে — মনে করে দেখো কোন কোডটা ঠিক এই পরিস্থিতির জন্য তৈরি হয়েছিলো, আর সেটা `raise HTTPException(...)` দিয়ে কীভাবে পাঠাতে হয়।

নিচে একটা কাঠামো দেয়া হলো, যেটা তোমার প্রজেক্ট শুরু করতে সাহায্য করবে — কিন্তু ইচ্ছাকৃতভাবে অসম্পূর্ণ রাখা হয়েছে, বাকিটা তোমার দায়িত্ব:

**সম্পন্ন হওয়ার শর্ত (Acceptance Criteria):** তোমার কাজটা তখনই সম্পূর্ণ ধরা হবে, যখন নিচের প্রতিটা আচরণ Postman, `curl`, বা FastAPI-এর `/docs` পেজ দিয়ে টেস্ট করে দেখানো যাবে। `POST /notes`-এ সঠিক `content` পাঠালে `201 Created` স্ট্যাটাসসহ নতুন তৈরি হওয়া নোটটা (তার `id` সহ) ফেরত আসবে। `POST /notes`-এ `content` ছাড়া পাঠালে FastAPI নিজে থেকেই `422 Unprocessable Entity` দেবে, আর খালি `content` (`""`) পাঠালে তোমার লেখা `@field_validator`-এর কারণে বোধগম্য একটা error বার্তাসহ error আসবে। `GET /notes` সবসময় এখন পর্যন্ত তৈরি হওয়া সব নোটের একটা লিস্ট ফেরত দেবে। `DELETE /notes/{note_id}` সঠিক `id` দিলে নোটটা মুছে যাবে আর উপযুক্ত সফলতার status code আসবে; ভুল বা অস্তিত্বহীন `id` দিলে যথাযথ error status code আসবে, `500` নয়। আর সবচেয়ে গুরুত্বপূর্ণ — কোডটা পড়ে যেন বোঝা যায় প্রতিটা ধাপ (validation, processing, storage, response) আলাদাভাবে চিন্তা করে লেখা হয়েছে, সব একটা জগাখিচুড়ি ফাংশনে গুঁজে দেয়া হয়নি।

এই অ্যাসাইনমেন্টটা শেষ করার পর তোমার হাতে থাকবে একটা কার্যকর, ছোট হলেও প্রকৃত API — আর তার চেয়েও গুরুত্বপূর্ণ, এই পুরো প্রক্রিয়াটা তোমার হাতে-কলমে অভিজ্ঞতা হয়ে যাবে, শুধু পড়া বিষয় হয়ে থাকবে না। তবে বাস্তব-জীবনের API আরও অনেক জটিলতা নিয়ে আসে — একটা নোট আপডেট করা, একাধিক ধরনের রিসোর্সের মধ্যে সম্পর্ক তৈরি করা, বড় তালিকাকে পাতায় পাতায় ভাগ করে দেখানো (pagination), আর ভুল হ্যান্ডলিং আরও সুসংগঠিতভাবে করা। এই সবকিছু নিয়েই আমরা এগিয়ে যাবো পরের মডিউলে — Module 7: API Development Part Two।
